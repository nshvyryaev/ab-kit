# Как вести эксперимент

Пошаговый порядок для хозяина, у которого ab-kit уже подключён (сервер,
клиент, показ варианта в аналитике). Подключение — `README.md`, устройство —
`docs/design.md`.

## 1. До кода: карточка эксперимента

Эксперимент начинается с записи, а не с конфига. В репозитории хозяина —
своя папка экспериментов (в «Цепочке слов» — `docs/experiments/`), один файл
на эксперимент:

- **гипотеза** — что меняем и почему ждём улучшения (с цифрами, откуда взялась
  идея);
- **варианты** — контроль и что именно меняется;
- **кто попадает** — правило записи (`enroll`). Обычно только новые: старожилы
  размывают сравнение;
- **главная метрика** — одна, как доля: «из записанных столько-то сделали X
  за N часов после показа». Вторичные — для понимания, решение по главной;
- **сколько ждать** — из `sampleSize` (ниже);
- **даты** — запуск, промежуточный взгляд, итог;
- **журнал** — результаты каждого взгляда и решение.

## 2. Сколько ждать: `sampleSize`

```js
import { sampleSize } from 'ab-kit/stats';
sampleSize({ p: 0.10, mde: 0.05 }); // 683 на вариант: 10% → 15% при α = 0,05 и мощности 80%
```

`p` — нынешняя доля по главной метрике (из аналитики), `mde` — наименьшая
разница, которую хотим заметить, в долях. Делим на поток записываемых игроков
в день на вариант — получаем дни. Если выходит месяц, а ждать столько нельзя,
честнее заранее сказать «увидим только крупный эффект», чем потом читать шум.

## 3. Конфиг

```js
{
  key: 'onboarding-v2',            // имя навсегда
  salt: 'onboarding-v2-2026-10',   // своя соль; не меняется, пока эксперимент жив
  status: 'running',
  variants: [
    { key: 'control', weight: 50 }, // первый — контроль: его получает всякий незаписанный
    { key: 'v2', weight: 50 },
  ],
}
```

Конфиг лежит в коде хозяина и меняется деплоем: кто и когда включил, видно в
истории git. Ошибка в конфиге роняет сервер при запуске, а не первый запрос.

## 4. Запуск

1. Клиент спрашивает вариант при запуске (не в момент показа — чтобы ответ
   успел), с `enroll` только для тех, кого записываем.
2. Экран выбирается по варианту; без ответа — контроль и **без** показа.
3. **Показ** (`ab_exposure { experiment, variant }`) уходит, когда вариант
   реально увиден, и только у записанных. По нему отчёт делит на группы.
4. Открытый экран не переключается, если ответ пришёл поздно: такой игрок в
   выборку не попадает.

## 5. Сразу после запуска — проверить доли

Через несколько часов, когда показов хотя бы сотня, отчёт хозяина печатает
доли групп и сверку с весами. Перекос (p < 0,01 при 50/50) — сбой записи
или показа, а не результат: эксперимент останавливают (`paused`) и чинят.

## 6. Промежуточный взгляд

Смотрим, но **не останавливаем по p-значению**: при частых взглядах «значимо»
случайно выскакивает гораздо чаще пяти процентов. Промежуточный взгляд нужен,
чтобы поймать поломку (у одного варианта метрика упала до нуля) и прикинуть,
хватит ли мощности к итоговой дате.

Читаем **доверительный интервал**, а не только p: интервал, накрывающий ноль,
значит «данных мало», а не «разницы нет».

## 7. Итог и решение

В назначенную дату — отчёт, запись в журнал карточки, решение:

- **победил вариант** — `status: 'concluded'`, `winner: '<вариант>'`: все,
  записанные тоже, получают победителя;
- **разницы не видно** — выбрать по продуктовым соображениям и тоже
  `concluded`; или продлить, если мощности не хватило и это видно по
  интервалу;
- **сломалось** — `paused` (новых не пишем, записанные остаются в своём
  варианте), чинить.

## 8. Уборка

Через деплой-другой после `concluded`, когда всем отдаётся победитель:

- удалить проигравший вариант из кода хозяина;
- удалить эксперимент из конфига (клиент без ответа покажет контроль, поэтому
  сначала победителя делают поведением по умолчанию);
- записи в хранилище не трогать: это история, по ней пересчитывается отчёт.

## Частые ошибки

| ошибка | чем плохо |
|---|---|
| сменить соль у живого эксперимента | незаписанные разложатся иначе, чем записанные |
| показ уходит при назначении, а не при показе | в группе окажутся те, кто экрана не видел |
| показ уходит у незаписанных | старожилы и отказы сервера попадут в контроль |
| остановить, как только p < 0,05 | частые взгляды дают ложную «победу» |
| главных метрик несколько | одна из них «победит» случайно |
| запрос варианта в момент показа | ответ не успевает, игрок видит контроль и выпадает |
