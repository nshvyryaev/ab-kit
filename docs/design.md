# ab-kit — дизайн первой версии

Простая система A/B-экспериментов: детерминированно и навсегда закрепляет за
игроком вариант эксперимента, помнит, кого куда записала, и даёт посчитать,
есть ли разница. Метрики не хранит — они живут в аналитике хозяина.

Первый потребитель — игра «Цепочка слов» (`E:\projects\word-chain`), первый
эксперимент — новое обучение против старого.

## Решения инженера

| вопрос | ответ |
|---|---|
| кто попадает в эксперимент с обучением | только новые: вариант назначается при первом входе в обучение; прошедшие обучение раньше в выборку не попадают; «Как играть?» показывает назначенный вариант |
| главная метрика | первый уровень пройден |
| как встраивается | пакет, как analytics-kit: отдельный репозиторий, подключается в сервер и клиент игры через github-тег, отдельного сервиса нет |
| как заводить и останавливать эксперименты | конфиг в коде игры, меняется деплоем |
| структура | место под другие языки; хранилище подменяемо |

## Что делает и чего не делает

Делает:

- **назначение** — какой вариант эксперимента у этого игрока;
- **закрепление** — назначенное не меняется, даже если потом поменять доли;
- **запись** — кто, в какой эксперимент, когда, какой вариант;
- **ответ клиенту** по HTTP и клиентский модуль, который этот ответ кеширует;
- **статистика** — сравнение двух долей (разница, доверительный интервал,
  p-значение) и оценка нужного размера выборки.

Не делает в v1: админку и включение без деплоя, таргетинг по сегментам
(кроме флага «записывать новых»), многорукие бандиты, хранение метрик и
отчёты с графиками. Метрики считает хозяин по своей аналитике, ab-kit даёт
ему только функцию сравнения.

## Понятия

- **Эксперимент** — `{ key, salt, status, variants, winner? }`.
  - `key` — имя, например `onboarding-v2`.
  - `salt` — соль хеша. Своя у каждого эксперимента, чтобы разбиения разных
    экспериментов не совпадали (иначе одни и те же игроки всегда попадали бы
    в «первую половину»).
  - `variants` — `[{ key, weight }]`; веса — целые, сумма любая, доли
    считаются от суммы. Первый вариант — контроль.
  - `status`:
    - `running` — назначаем и записываем новых;
    - `paused` — новых не записываем (им контроль), у записанных вариант тот же;
    - `concluded` — всем, и записанным тоже, `winner`.
- **Единица** (unit) — непрозрачная строка от хозяина: кому назначаем. В игре —
  псевдоним игрока из аналитики (`subject`), чтобы назначение напрямую
  сопоставлялось с событиями.
- **Назначение** — `{ experiment, unit, variant, assigned_at }`. Пишется один раз.

## Алгоритм назначения

Один для всех языков, описан в `spec/` и закреплён тестовыми векторами.

```
h       = SHA-256( "ab:v1:" + salt + ":" + unit )   // UTF-8
bucket  = uint32 big-endian из первых 4 байт h, mod 10000
variant = первый вариант, у которого bucket < накопленная доля * 10000
```

Накопленная доля считается в целых: `floor(10000 * сумма весов до варианта
включительно / сумма всех весов)`. У последнего варианта граница всегда
10000, чтобы округление не оставляло ведро без варианта.

Назначение детерминировано, но решает не хеш, а **запись**: при первом
назначении вариант пишется в хранилище, и дальше отдаётся записанный. Поэтому
смена долей на ходу не перебрасывает уже записанных игроков. Хеш нужен, чтобы
повторный запрос до записи (гонка двух вкладок) дал тот же ответ.

## Поведение `assign`

```
assign(experiment, unit, { enroll })
```

1. Эксперимента нет в конфиге → `{ variant: null }`, хозяин показывает своё
   поведение по умолчанию.
2. `concluded` → `{ variant: winner, enrolled: false }`.
3. Есть запись → `{ variant: записанный, enrolled: true }`.
4. Записи нет, `enroll` и `running` → вычислить, записать (вставка, если
   ещё нет; при гонке побеждает первая запись), вернуть
   `{ variant, enrolled: true }`.
5. Иначе → `{ variant: контроль, enrolled: false }`.

Ошибка хранилища или любая другая — не исключение наружу, а
`{ variant: контроль, enrolled: false, error: true }`. Эксперимент не имеет
права ронять игру или задерживать её запуск.

Признак `enrolled` и есть граница выборки: в анализ идут только записанные.
Игроки, получившие контроль без записи (старожилы, отказ сервера), в отчёт не
попадают.

## Хранилище — подменяемое

Интерфейс:

```js
store.get(experiment, unit)         // → { variant, assigned_at } | null
store.claim({ experiment, unit, variant, assigned_at })
                                    // вставить, если нет; вернуть то, что лежит
store.count(experiment)             // → { [variant]: n } — для контроля долей
store.close()
```

Реализации v1: SQLite (`node:sqlite`, без зависимостей — как в analytics-kit)
и память (для тестов и как образец). Новая БД — новый модуль с тем же
интерфейсом. Пакет экспортирует **общий набор контрактных тестов**
(`runStoreContract(makeStore)`): любая новая реализация обязана его пройти,
иначе подмена хранилища тихо сломает закрепление.

## Части пакета (реализация на JS)

- `core` — алгоритм назначения, проверка конфига, `assign` поверх хранилища.
  Без ввода-вывода.
- `server` — `createAbHandler({ experiments, store, resolveUnit })`:
  обработчик `POST /v1/ab/assign` для `node:http`. Кто такой игрок, решает
  хозяин через `resolveUnit(request, body)`: личность в игре уже
  устанавливается по подписи площадки, и дублировать это в ab-kit нельзя.
- `store/sqlite`, `store/memory`, `store/contract` (контрактные тесты).
- `browser` — `createAbClient({ endpoint, storage, timeoutMs })`:
  запрашивает варианты, кеширует последний ответ в хранилище площадки, при
  таймауте или ошибке отдаёт кеш или контроль. Без зависимостей, маленький.
- `stats` — `compareProportions`, `sampleSize`.

### Протокол

```
POST /v1/ab/assign
{ "experiments": ["onboarding-v2"], "enroll": ["onboarding-v2"], ...поля хозяина }
→ 200 { "assignments": { "onboarding-v2": { "variant": "v2", "enrolled": true } } }
```

`enroll` — подмножество `experiments`: в каких записывать, если записи ещё
нет. Поля хозяина (параметры запуска, анонимный id) ab-kit не читает, их
читает `resolveUnit`. Если хозяин не установил игрока — `assignments` с
контролем и `enrolled: false` по каждому эксперименту.

## Структура репозитория

```
ab-kit/
├── spec/                 общее для всех языков
│   ├── README.md         алгоритм, протокол, формат конфига
│   └── vectors/          тестовые векторы: (salt, unit, веса) → ведро, вариант
├── js/                   реализация на JS (Node ≥ 22 и браузер)
│   ├── src/{core,server,browser,store,stats}/
│   └── tests/
├── <другой язык>/        будущая реализация рядом, проходит те же векторы
├── docs/
│   ├── design.md         этот файл
│   └── acceptance/       критерии приёмки (плагин acceptance)
└── package.json          в корне: npm ставит пакет из git только по корневому
                          package.json; exports указывают в js/src
```

Корневой `package.json` — вынужденная мера: `npm install github:…#tag` ищет
манифест в корне репозитория. Он принадлежит JS-реализации и не мешает
другим языкам: у них свои манифесты в своих папках.

## Встраивание в «Цепочку слов»

Это работа на стороне игры, со своими критериями в её репозитории.

1. **Конфиг** `server/src/experiments.mjs`:
   `onboarding-v2`, соль `onboarding-v2-2026-10`, варианты `control` 50 /
   `v2` 50, `running`.
2. **Сервер:** ручка `/v1/ab/assign` через `createAbHandler`. `resolveUnit` —
   тот же псевдоним, что у аналитики: подписанные параметры запуска →
   псевдоним игрока, иначе анонимный id → анонимный псевдоним. Хранилище —
   отдельный файл SQLite в `/data` рядом с кошельком и аналитикой; резервная
   копия — тем же `backup.sh`.
3. **Клиент:** при запуске, пока игрок не прошёл обучение, — запрос с
   `enroll: ['onboarding-v2']`; прошедшему — без `enroll` (только чтобы «Как
   играть?» показал его вариант). Обучение выбирает экран по варианту; без
   ответа — старое обучение.
4. **Аналитика:** событие `ab_exposure { experiment, variant }` в схеме
   analytics-kit — в момент, когда вариант реально показан (вход в
   обучение). Отчёт связывает его с событиями по `subject`.
5. **Отчёт:** скрипт только для чтения, как воронка обучения: по вариантам —
   показано игрокам, главная метрика, вторичные, и `compareProportions`.

### Метрики эксперимента с обучением

- **Главная:** доля записанных игроков, прошедших хотя бы один уровень
  (`level_end`, `outcome: solved`, не учебный) в течение 24 часов после
  показа.
- **Вторичные:** доля дошедших до игры (вышли из обучения в уровень); доля
  прошедших обучение до конца; доля пропустивших; вернувшиеся на
  следующий день.

### Сколько ждать

По аналитике на 3 октября: новых игроков около 200 в день (день запуска —
221), первый уровень проходит около 10%. При 95% надёжности и 80% мощности:

| хотим заметить | игроков на вариант | при ~200 новых в день |
|---|---|---|
| 10% → 20% (вдвое) | ~200 | ~2 дня |
| 10% → 15% (+50%) | ~680 | ~7 дней |
| 10% → 12% (+20%) | ~3800 | ~5–6 недель |

За два дня видна только очень крупная разница. Отчёт будет показывать
доверительный интервал, а не только «победил/не победил», — так видно, что
данных пока мало, а не что разницы нет.

## Чего опасаемся

- **Утечка выборки:** «Как играть?» у старожила не должен записывать его в
  эксперимент. Решается тем, что `enroll` шлёт только непрошедший обучение.
- **Повторная запись:** один человек на двух площадках — два `subject`, два
  назначения. Принимаем: единица — аккаунт площадки, как и в аналитике.
- **Сбой сервера в момент записи:** игрок получает контроль без записи и в
  анализ не идёт; доли вариантов в отчёте сверяются с весами — перекос
  виден сразу.
- **Ответ не успел к началу обучения:** запрос уходит при запуске игры, а не
  при входе в обучение; таймаут короткий; без ответа — старое обучение и без
  записи.
